# AGENTS.md

Guide for coding agents working on this repository. If you only want to call the API from an agent, read [.agents/skills/mt5-httpapi/SKILL.md](.agents/skills/mt5-httpapi/SKILL.md) instead; this file is about changing the code.

The project rules live in [.agents/rules/](.agents/rules/README.md), one file per topic. Read the ones that match what you are about to touch before you edit.

## What this project is

mt5-httpapi runs real Windows MetaTrader 5 terminals inside a `dockurr/windows` VM in Docker and puts an HTTP REST API and MCP servers in front of them.

- **One API process per terminal.** Each configured terminal gets its own Python process inside the VM (`python -m mt5api`, started by `scripts/api_runner.bat`). It is a Flask app (`mt5api/server.py`) served by waitress (`mt5api/main.py`), talks to the terminal through the `MetaTrader5` SDK, and serializes every SDK call behind one process-wide lock (`with_mt5` and `session()` in `mt5api/mt5client.py`, which answer 503/504 on queue overflow, wedge or timeout).
- **nginx in front.** One port (8888 on the host) routes `/<broker>/<account>/<instance>/` and, for the `default` instance, `/<broker>/<account>/` to that terminal's API port inside the VM. The config is generated by `scripts/config_helper.py nginx_conf`; unknown paths answer `404 no route`.
- **Per-terminal MCP.** Each API process also mounts a FastMCP server (`mt5api/mcp_server.py`) at `/mcp` through an a2wsgi bridge in `mt5api/main.py`, with the same bearer check as REST. Its tools call the Flask app in process through a WSGI test client, so they run the exact REST handlers.
- **Unified MCP.** `mcpunifier/` is a separate FastAPI + httpx service in its own image (`Dockerfile.mcpunifier`, port 6600) that nginx exposes at `/mcp/`. Every tool takes `broker`, `account` and optional `instance` and proxies over HTTP to the right terminal. It reads the same `config/config.yaml`.
- **wickworks sidecar.** A pinned `psyb0t/wickworks` container shares the VM container's network namespace and computes the technical analysis behind `POST /symbols/<symbol>/rates/ta`. `scripts/wickworks-healthcheck.py` detects when it is stuck in an orphaned namespace after a VM recreate.
- **vm-watchdog.** A compose service (`scripts/vm-watchdog.py`, `Dockerfile.watchdog`) that recreates a VM container only after Docker health has stayed unhealthy for a sustained streak, through `scripts/recreate-vm.sh`.
- **Health monitor.** `mt5api/monitor.py` checks the terminal every 60 seconds inside each API process and restarts it after 5 dead checks. In the VM a second thread checks every 10 seconds whether `terminal64.exe` is a new process (LiveUpdate, an SDK-started or hand-started terminal); if so it reconnects the SDK and re-applies the WebRequest allowlist.

### Configuration

`config/config.yaml` is the single config file (template: `config/config.yaml.example`). It holds the API token, the compile settings, the accounts, the terminal list (broker, account, instance, port, `utc_offset`, `mode: live|backtest`, `symbol_suffix`, per-terminal feature overrides) and the optional feature blocks. It is gitignored and holds broker credentials: never read it, print it or commit it. Optional `vms.yaml` (template `vms.yaml.example`) splits terminals across several VMs.

`scripts/config_helper.py` is the only thing that turns that file into other config. Its subcommands include `terminals` (what `start.bat` launches), `write_ini` (the per-terminal `mt5start.ini` with login, plus the Chart Deployments `[StartUp]` block), `nginx_conf`, `generate_compose` (renders `docker-compose.yml.j2` when `vms.yaml` exists), `vm_group`, `port_list` and `chartctl_enabled`. It runs both on the host and inside the VM, so it cannot import `mt5api`; rules it shares with `mt5api/config.py` (such as `_feature_block`) are duplicated on purpose and must stay identical.

### How code reaches the VM

The VM does not see the repo. `run.sh` (what `make up` runs) copies `config/config.yaml`, the broker installers from `mt5installers/`, the Windows scripts from `scripts/` and the whole `mt5api/` package into `data/shared/`, which the VM mounts. `assets/` is mounted read-only at `/shared/assets`. It then generates the nginx config and per-VM group files, and runs `docker compose up -d --build` (asking first if the stack is already up, and taking it down to restart). Inside Windows, `start.bat` runs on every logon: it takes a boot-scoped lock through `scripts/acquire_lock.ps1`, calls `install.bat` (idempotent prerequisites, Python, the MT5 installs; `*.done` flags in `data/shared` mark finished steps), installs the pip requirements, compiles the Chart Deployments loader when enabled, launches each terminal after writing its `mt5start.ini` through `config_helper.py write_ini`, and starts one `api_runner.bat` per terminal. The boot order and its rules are in [windows-vm.md](.agents/rules/windows-vm.md). A Python change therefore needs `make up` (or a VM restart after copying) before the running stack sees it.

### Optional features

Each is off unless `config.yaml` turns it on, and its routes do not exist when it is off.

- **Chart Deployments** (`chartctl.enabled: true`, live-mode terminals only, `chartctl: false` on a terminal opts it out): upload `.ex5` and `.set` files, declare deployments, and let the loader EA `assets/experts/MT5ChartLoader.mq5` (with `assets/experts/include/ChartControl.mqh`) reconcile charts over a file protocol. Routes in `mt5api/handlers/chartctl_routes.py`, logic in `mt5api/chartctl/`. The WebRequest allowlist routes come with it and are applied in the terminal's Options dialog with window messages (`mt5api/chartctl/winoptions.py`).
- **File API** (`files.enabled: true`, `files: false` on a terminal opts it out, any mode): list, read, write, unzip and delete files in the terminal tree (`/files/...`) and the compile tree (`/compile/files/...`). Routes in `mt5api/handlers/files.py`, logic in `mt5api/fileapi/`.
- **Compile** (`POST /compile`, always registered): MQL5 source in, `.ex5` out, through MetaEditor. Tuned by `compile_api_token`, `compile_timeout`, `compile_max_source_bytes`, `compile_terminal_dir`, `compile_include_dir`, `compile_work_dir`, `compile_local_cache` and `compile_include_digests` (env var of the same name in upper case wins). Code in `mt5api/handlers/compile.py`.

The enable rules live in `chartctl_enabled()` and `files_enabled()` in `mt5api/config.py`, and `mcpunifier/config.py` applies the same rules.

## Build, run, test

Run `make help` for the list. The targets:

| Target | What it does |
| --- | --- |
| `make up` | `./run.sh`: copy code and config into `data/shared`, generate nginx and compose config, start or restart the stack. |
| `make down`, `make logs`, `make status` | Stop the stack, follow logs, check VM and API health (`scripts/status.sh`). |
| `make lint` | `scripts/lint.sh` in a throwaway image with the repo mounted read-only: non-ASCII gate on `.ps1`, `.bat` and `.cmd`, `.ps1` parse check, PSScriptAnalyzer, shellcheck and shfmt on `.sh`. There is no Python linter in CI; `ruff check --select E,F,W,B --line-length 100` on `mt5api/`, `mcpunifier/` and `scripts/` is clean and should stay that way. |
| `make format` | shfmt in place on the same file set. |
| `make test` | The full gate CI runs: `verify-binaries`, `test-unit`, `test-integration`, `test-go`. |
| `make verify-binaries` | `scripts/verify_binaries.py` on the host against `assets/binaries.lock.json`. |
| `make test-unit` | Builds `Dockerfile.test` and runs `pytest tests/` without `tests/live` and `tests/integration`, with coverage on `mt5api` and a floor of 62 percent (`--cov-fail-under`). |
| `make test-integration` | Host venv in `.venv-test`, then `pytest tests/integration/`: nginx routing against the generated config, the unifier image beside a stub terminal (tool surface, catalog against Flask's `url_map`, a down terminal failing alone), the vm-watchdog recovery and the wickworks sidecar lifecycle on disposable compose projects. Needs the Docker socket. |
| `make test-go` | `go test -race ./...` on `clients/go` in a pinned Go image. |
| `make test-live` | `pytest tests/live/` against a running stack set by `MT5_LIVE_URL`, `MT5_LIVE_TOKEN`, `MT5_LIVE_BROKER`, `MT5_LIVE_ACCOUNT` and the other `MT5_LIVE_*` variables, or `tests/live/.env`. Pick modules with `LIVE_TESTS=...`, pass pytest args with `LIVE_ARGS=...`. Places real orders. |

The `MetaTrader5` SDK is Windows only, so `tests/conftest.py` installs a stub module with the SDK constants before any `mt5api` import, and tests script SDK return values through its `RecordedMT5`, `api_client` and `patch_handler` fixtures. `pytest.ini` keeps `tests/live` and `tests/integration` out of the default collection. Details on the live suite: [docs/operations.md](docs/operations.md#testing-a-running-stack). Which layer to use for what: [.agents/rules/testing.md](.agents/rules/testing.md).

## Conventions that matter

Short list. Each has a rule file with the details and the tests that enforce it.

- **JSON keys are snake_case**, the same as the MT5 fields passed through. Backtest and TA responses still carry the old camelCase keys beside them through `mt5api/jsonkeys.py`, and their request bodies accept both forms (different values under both names is a 400). The camelCase keys are deprecated; never add new ones. See [api-design.md](.agents/rules/api-design.md).
- **Errors are JSON with an `error` string**; newer routes (chartctl, files) add a machine-readable `code`. `/compile` answers `{ok, log}` instead. See [api-design.md](.agents/rules/api-design.md).
- **Feature routes are registered only when their flag is on** (`server.py`), and the MCP tools follow the same gate on the per-terminal server.
- **The two MCP servers expose the same tools with the same parameters**, the unified copy adding `broker`, `account` first and `instance` last (`tests/test_mcp_tool_parity.py`). The unifier's hand-written route catalog must match the Flask routes (`tests/integration/test_mcpunifier.py`). See [mcp.md](.agents/rules/mcp.md).
- **Windows-side files are ASCII only.** An em dash in `acquire_lock.ps1` once mojibaked under Windows PowerShell 5.1, threw a parse error that `start.bat` read as "lock held", and deadlocked every boot; `make lint` now fails on non-ASCII in any `.ps1`, `.bat` or `.cmd`. See [windows-vm.md](.agents/rules/windows-vm.md).
- **Live accounts are real money.** Order, position, terminal and deployment calls act on a real broker account. Never run them, or `make test-live` order modules, against anything but a demo account unless the user said so for that run. See [security.md](.agents/rules/security.md) and [testing.md](.agents/rules/testing.md).
- **Docs move with the code** in the same change, and prose carries no em or en dashes. See [docs-and-releases.md](.agents/rules/docs-and-releases.md).

## Common changes

Adding a REST route:

1. Write the handler in the matching `mt5api/handlers/` module; wrap it in `@with_mt5` if it calls the SDK (ARC2).
2. Register it in `mt5api/server.py`, or in the feature's register function if it is gated (ARC12).
3. Add it to the unifier catalog in `mcpunifier/mcp_server.py` (MCP4). If an agent should call it directly, add a typed tool to both MCP servers with identical parameters (MCP1).
4. If it can run past 60 seconds, add it to `LONG_RUNNING_ROUTES` in `scripts/config_helper.py` (ARC16).
5. Add unit tests, and live tests if only a real terminal shows the behaviour (TST1, TST9). Update the owning doc and the CHANGELOG (DOC1, DOC10).

Adding a config setting:

1. Read it in `mt5api/config.py` (and `mcpunifier/config.py` if the unifier needs it) with a safe default (PY4).
2. Document it in `config/config.yaml.example` and [docs/installation-and-configuration.md](docs/installation-and-configuration.md) or the feature's doc.
3. If it changes generated nginx, compose or INI output, change `scripts/config_helper.py` and `tests/test_config_generation.py` together (ARC8, ARC9).

Changing a Windows script:

1. Keep it ASCII (WIN1, WIN2) and idempotent across boots (WIN4).
2. If it is new, add it to the copy list in `run.sh` (WIN8).
3. Run `make lint` for `.ps1` and `.sh` changes. Nothing in CI boots Windows, so say in the change what you could not test.

Adding a vendored binary: declare it in `assets/binaries.lock.json` with its provenance and run `make verify-binaries` (SEC12).

## Releases

- `CHANGELOG.md` gets a section per release, newest first: `## [vX.Y.Z]: YYYY-MM-DD`, then `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed` or `### Security` as needed. Each bullet says what changed for the user, opens with a bold summary for anything notable, and links the doc that covers it. Semantic versioning: patch for fixes and docs, minor for compatible features, major for breaking changes.
- The version lives in `.agents/.codex-plugin/plugin.json`, `.agents/plugins/mt5-httpapi/package.json` and `.agents/plugins/mt5-httpapi/openclaw.plugin.json`; bump all three together. `.agents/.claude-plugin/plugin.json` carries no version.
- Each release is an annotated tag `vX.Y.Z` whose message is the version on the first line, a blank line, then that CHANGELOG section's bullets.
- `.github/workflows/pipeline.yml` runs on pushes to `master`, on `v*` tags and on non-draft pull requests: `test` (`make test`), `lint` (`make lint`), `badges` (on the default branch and tags), and `clawhub`, which after `test` and `lint` pass validates the skill and the plugin on every run and publishes both to ClawHub only on a tag. Fork pull requests skip `clawhub`. Before building, `test` and `lint` log in to Docker Hub through `scripts/ci-dockerhub-login.sh` with the `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` secrets, because anonymous pulls from GitHub's shared runner IPs hit Docker Hub's rate limit; the script retries and falls back to anonymous pulls, and fork pull requests pull anonymously. `mirror-and-archive.yml` and `issue-pull.yml` are housekeeping workflows.

Never tag, push or publish unless the user asked for that specific action.
